# 待处置：剩下的 112 个悬空目标**不是建页 backlog**

发现时间：2026-09-21（收尾「56 个」时顺查出来的）
发现方式：建完 56 个之后第八类仍有 115 行，去核这 115 行到底是什么。

## 现象：三个数字恰好对上

| 量 | 数 |
|---|---|
| `extract/prose-allowlist.txt` 行数 | 524 |
| `wiki/` 下已建页 stem 数 | 412 |
| **两者之差** | **112** |
| `extract/dangling.csv` 真实悬空目标数（扣掉 2 行注释与 1 个空目标 `…`） | **112** |
| 交集（悬空目标 ∩ 差集） | **112（完全同一批）** |

**也就是说：`allowlist = 已建 ∪ 悬空`，一一对应，没有第三个来源。**
而且 `extract/wiki-plan.csv` **267 行 100% 建成**（`plan_sync.py --write` 跑完 `plan−已建 = 0`）。

**所以这 112 个的处境是**：它们**在 allowlist 里**（于是写页的人认为「链它是安全的」），
却**不在建页计划里**（`wiki-plan.csv` 是「建什么」的唯一记录，§12）。
**没人会给它们建页——不是不可能建，是没人登记要建。**

## 它们各自是什么（机械分类，112 个全部有根）

| 类 | 数 | 判据 | 例子 |
|---|---|---|---|
| **有同名定义文档** | **41** | 语料里存在标题与 slug 完全同名的 `.md` | `add-limit` → `02.07.04.01.02_addLimit.md`；`hw-state` → `02.07.04.01.117_HW_STATE.md`；`debug-view`；`smartest-data-formatter`；`smartshell` |
| **是某文档标题的子串（多为别名 / 单复数）** | **71** | slug 归一后是某标题的子串 | `data-logging-profile` ⊂ `Loading a data logging profile`；`technology-file` ⊂ `Technology file for a device` |
| **语料里无根** | **0** | — | — |

**0 个凭空**——所以这 112 个都不是误收，都是语料里真有的东西；
问题**只在「没人登记要建」这一步**。

## 归类

按本工程的对账规矩，这是 **(b) 基线工具不精确**——**但锅在规格，不在脚本**：

`extract/PROSE-SPEC.md` 第 4 条的原话是
「链一个清单外的名字 = 造一个**永远不会建的悬空目标**」。
**这句话把 allowlist 当成了「将来都会建的名字」的集合，而实测它不是**——
它是「语料里有根的名字」∪「已建页」。**112 个在清单内、却永远不会建**，
**恰好是这条规则声称要防的东西。**

**后果链条**：写页的人照规则办事（只用清单内的名字）→ 清单里有 112 个不可建的 →
链接照建 → 第八类照红。**规则本身在制造它要防的那件事。**

> 同一天还查出另一件事，形状一样：`verify_stages.py` 第八类把
> **行内代码跨度里的 wikilink 照样算链接**（这是**故意的**，注释里写明了理由），
> 而 `extract/.pagecheck.py` 会先把代码跨度剥掉再找链接——
> **于是「讲某条链已经拆掉」的散文，会把那条悬空目标原样造回来，而自检工具看不见。**
> 2026-09-18 踩过一次（`ddic`），2026-09-21 又踩一次（`data-logging-profile`，见下）。
> `.pagecheck.py` 已按第八类的口径补上这一条（只报**会造成悬空**的那些）。

## 已经被它害到的一次（2026-09-21）

「56 个」里那 1 个链接修正是 `data-logging-profile` → `data-logging-profiles`。
判定依据是：**计划表里只有复数那一行**，单数名永远不会建。
修完之后，我在解释这次修正的散文里**写了一次 `[[data-logging-profile]]`**
（在反引号里，自以为安全）——**第八类把代码跨度里的也算，于是那条悬空目标当场被造回来**。
是 `verify_stages.py` 的口径注释把它拦下来的，`.pagecheck.py` 当时看不见。

## 建议的处置（未执行，等定夺）

**这 112 个不能整批处理，必须逐类分**：

1. **41 个有同名定义文档的** —— 大概率**该补计划行**（它们是真对象：L2 API、GUI 视图、工具），
   建页判据、层、阶段仍需人判（§2 / §6：`type`/`layer`/`stage` 是人的判断，不许下放给 agent）。
2. **71 个别名 / 单复数** —— 大概率**该改链**指向已有的页（像 `data-logging-profile` 那样），
   改完再把这 71 个从 allowlist 里去掉，**否则下一个写页的人还会链它们**。
3. **两个动作都要有**：只改链不去名 = 下一个人再犯；只去名不改链 = 现有链接变成
   `.pagecheck.py` 能看见的违规（**这是好事**，比现在「清单内却不可达」的隐形状态好）。

**顺序建议**：先做 2（改链 + 从 allowlist 去名，机械、可核），
再对 1 逐条判「值不值得建页」——**建页是人的判断，不是清账的副产品**。

## 为什么没有当场就改

- **改 allowlist 会改变全部 412 页的链接合法性判据**，
  而此刻正有一批写页工作刚落盘（56 页）。**这时候动清单，分不清是谁造成的红。**
- 41 个到底哪些建、建成什么层，是 §2/§6 明令**不许下放给 agent** 的判断。
- 所以先落成这一份记录，把数、分类、原因、两条处置路径都钉死。
