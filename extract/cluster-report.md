## 第六类 · 装得下的主题有没有被切散（**穷举**）

判据来自切分规则的逆否：**体量 ≤ 预算的前缀节点必须完整落在一个簇里**。
违反 = 一个本来读得下的主题被拆到两个簇 = 两边各写半页。
体量 > 预算的节点**必须**被拆（不拆塞不进任何一次调用），拆了不算错。

| 检查 | 期望 | 实测 |
|---|---|---|
| 语料里的前缀节点总数 | — | 9,394 |
| 其中体量 ≤ 预算（**必须不被拆**） | — | 9,353 |
| **被拆到多个簇的** | 0 | **0** |
| 其中体量 > 预算（**必须被拆**，不算错） | — | 41 |

**9,353 个读得下的主题，一个都没被拆散。**

体量 > 预算、**必须**被拆的节点（拆对了才读得进去）：

- `02` 6,585,514 token / 8316 篇 = 预算的 65.9 倍
- `02.07` 1,877,422 token / 2318 篇 = 预算的 18.8 倍
- `02.07.04` 1,125,187 token / 1314 篇 = 预算的 11.3 倍
- `02.07.04.01` 1,097,484 token / 1291 篇 = 预算的 11.0 倍
- `02.06` 987,880 token / 975 篇 = 预算的 9.9 倍
- `02.08` 827,603 token / 1144 篇 = 预算的 8.3 倍
- `03` 801,473 token / 573 篇 = 预算的 8.0 倍
- `02.08.04` 779,005 token / 1069 篇 = 预算的 7.8 倍

佐证 · 按分类号排全库，9,393 篇共 150 次簇切换；**69/101** 簇恰好占一段连续区间。

这个数字**自己就不稳**：换排序键它会变（按完整路径排是 93/101，按分类号元组排是 69/101）。原因有两个，都不是错误——

1. **字典序假碎片**：`26` 排在 `250` 之后（逐字符比 `6`>`5`），所以 `.26_x` 会「跳」到 `.250` 那批后面，看上去像碎了一段。
2. **真碎片只在允许拆的地方**：碎成 2~3 段的簇全在 `02.07.04.01`（11 倍预算）和 `02.06.02.02` 内部——那里**必须**拆。

所以它是佐证，不是判据：**判据是第六类那张表**，它不依赖任何排序键。
